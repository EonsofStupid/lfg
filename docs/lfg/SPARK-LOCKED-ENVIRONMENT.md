# GB10 locked environment and model preparation

On 2026-10-31, the existing `Clyffy-Ring` host was reachable as Linux aarch64
with an NVIDIA GB10 and driver 580.178.04. The existing SWAG container was
running before and after these checks. The checks did not establish uninterrupted
service availability or train on private project records.

An isolated directory at `~/lfg-training-lab/gb10-locked-env-20261031-v1`
contains a 78-wheel, 2.8 GiB ARM64 wheelhouse, two virtual environments, and a
local model snapshot. The resolved
[wheel lock](../../ml/lfg-encoder/locks/linux-arm64-gb10-py312.requirements.txt)
has SHA-256 `85dfdbe37d6609cd7abdd9f07935d78d23fbde04163dc7d7eb2fe5d32a947e8f`.
Its [constraints](../../ml/lfg-encoder/locks/linux-arm64-gb10-py312.constraints.txt)
select PyTorch 2.11.0, Transformers 4.57.6, datasets 4.8.5 and accelerate
1.15.0; other resolved versions are in the lock. Wheels were acquired from
PyPI, then both Python 3.12 environments were installed from the local
wheelhouse using `--no-index --require-hashes`. Both passed `pip check` and the
installed-wheel payload verifier. Each verifier matched 27,325 files totaling
5,107,746,248 bytes, with identical installed-version and payload digests; 78
installer records and three scripts were excluded. This is same-host
repeatability, not verification of the interpreter, generated bytecode,
bootstrap pip, upstream publisher identity or another machine.

The first environment reported PyTorch `2.11.0+cu130`, CUDA runtime 13.0,
GB10 compute capability 12.1 and finite CUDA forward/backward results on a small
tensor. PyTorch lists `sm_120` among its compiled architectures; that single
operation does not qualify every required kernel or workload. PyTorch describes
its [CUDA-enabled Linux aarch64 packages](https://pytorch.org/blog/vllm-and-pytorch-work-together-to-improve-the-developer-experience-on-aarch64/);
NVIDIA's [CUDA compatibility table](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)
identifies driver-family requirements and compatibility limits.

The project's configured [ModernBERT-base](https://huggingface.co/answerdotai/ModernBERT-base)
was acquired at revision `8949b909ec900327062f0ebf497f51aef5e6f0c8`.
The model card reports Apache-2.0. Six explicitly selected files were copied to a
link-free snapshot and checked against the repository's Git-blob or LFS metadata;
the weights' SHA-256 matches the published LFS SHA-256
`340ac08b74eef0d7bdec2d7981a6a3d4249bf0e6aab60634b72ad02c2b8023a9`.
The [snapshot manifest](../../ml/lfg-encoder/locks/modernbert-base.8949b909.manifest.json)
and [source evidence](../../ml/lfg-encoder/locks/modernbert-base.8949b909.provenance.json)
identify those files. HTTPS metadata and content hashes establish consistency
with the repository response, not an independent signature or license review.
The user-selected model, revision and file list remain inputs to
`fetch_model_snapshot.py`; no weights or private project data are committed.

The second locked environment loaded this snapshot offline with the project's
current 13-label taxonomy. A one-token, in-memory forward/backward probe on CUDA
returned finite `[1, 13]` logits for 149,614,861 parameters; PyTorch reported
1,525,710,336 peak allocated CUDA bytes for that probe, including checks that
all produced gradients were finite. The classification head was newly
initialized. The [aggregate probe report](evidence/modernbert-gb10-runtime-probe.v2.json)
contains its identities. This is neither training nor a 512-token performance
measurement, and the untrained head cannot make qualified predictions.

On 2026-10-31, the trainer's explicit device selection was also checked in the
locked Spark environment without loading training examples or starting a run.
In the helper version used for that historical check, `cuda` selected `cuda:0`
and `cpu` selected `cpu`; with CUDA hidden, an explicit `cuda` request failed
before creating its output directory. That helper check did not establish that
the full trainer permitted CPU execution. The current trainer is GPU-only and
rejects CPU configuration for both GPU-present and GPU-absent hosts. This checks
target selection, not a completed training job or GPU
memory capacity. The selected target is a configurable run input documented in
the [trainer instructions](../../ml/lfg-encoder/README.md#checkpointing-and-restart).

A subsequent check on the same Spark exercised the current trainer's device
selection with the real Transformers `TrainingArguments` in the locked
environment. With the GB10 visible, both `auto` and `cuda` selected CUDA; with
`CUDA_VISIBLE_DEVICES=-1`, both were rejected. `cpu` was rejected in both cases.
The copied trainer had SHA-256
`da8c06f34e9e83a578072ee75176dfba7e31ffe8f36b4ea76f4f7765ce392ac4`.
No project examples were transferred and no model training took place.

Re-run the probe with the copied scripts and selected files in the isolated
directory, changing paths and settings as appropriate:

```bash
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 TOKENIZERS_PARALLELISM=false \
  venv-repro/bin/python probe_model_runtime.py \
  --model modernbert-base-v2 --model-manifest modernbert-base-v2.manifest.json \
  --revision 8949b909ec900327062f0ebf497f51aef5e6f0c8 \
  --taxonomy evaluation-taxonomy.v1.json --device cuda --threads 2 --tokens 1 \
  --seed 731 --output NEW_PRIVATE_REPORT.json
```
