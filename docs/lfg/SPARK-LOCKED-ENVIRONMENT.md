# GB10 locked environment and model preparation

On 2026-10-31, the existing `Clyffy-Ring` host was reachable as Linux aarch64
with an NVIDIA GB10 and driver 580.178.04. The existing SWAG container was
running before and after these checks. The checks did not establish uninterrupted
service availability or train on private project records.

An isolated directory at `~/lfg-training-lab/gb10-locked-env-20261031-v1`
contains a 78-wheel, 2.8 GiB ARM64 wheelhouse, two virtual environments, and a
local model snapshot. The resolved
[wheel lock](../../ml/lfg-encoder/locks/linux-arm64-gb10-py312.requirements.txt)
has SHA-256 `85dfdbe37d6609cd7abdd9f07935d78d23fbde04163dc7d7eb2fe5d32a947e8f`.
Its [constraints](../../ml/lfg-encoder/locks/linux-arm64-gb10-py312.constraints.txt)
select PyTorch 2.11.0, Transformers 4.57.6, datasets 4.8.5 and accelerate
1.15.0; other resolved versions are in the lock. Wheels were acquired from
PyPI, then both Python 3.12 environments were installed from the local
wheelhouse using `--no-index --require-hashes`. Both passed `pip check` and the
installed-wheel payload verifier. Each verifier matched 27,325 files totaling
5,107,746,248 bytes, with identical installed-version and payload digests; 78
installer records and three scripts were excluded. This is same-host
repeatability, not verification of the interpreter, generated bytecode,
bootstrap pip, upstream publisher identity or another machine.

The first environment reported PyTorch `2.11.0+cu130`, CUDA runtime 13.0,
GB10 compute capability 12.1 and finite CUDA forward/backward results on a small
tensor. PyTorch lists `sm_120` among its compiled architectures; that single
operation does not qualify every required kernel or workload. PyTorch describes
its [CUDA-enabled Linux aarch64 packages](https://pytorch.org/blog/vllm-and-pytorch-work-together-to-improve-the-developer-experience-on-aarch64/);
NVIDIA's [CUDA compatibility table](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)
identifies driver-family requirements and compatibility limits.

The project's configured [ModernBERT-base](https://huggingface.co/answerdotai/ModernBERT-base)
was acquired at revision `8949b909ec900327062f0ebf497f51aef5e6f0c8`.
The model card reports Apache-2.0. Six explicitly selected files were copied to a
link-free snapshot and checked against the repository's Git-blob or LFS metadata;
the weights' SHA-256 matches the published LFS SHA-256
`340ac08b74eef0d7bdec2d7981a6a3d4249bf0e6aab60634b72ad02c2b8023a9`.
The [snapshot manifest](../../ml/lfg-encoder/locks/modernbert-base.8949b909.manifest.json)
and [source evidence](../../ml/lfg-encoder/locks/modernbert-base.8949b909.provenance.json)
identify those files. HTTPS metadata and content hashes establish consistency
with the repository response, not an independent signature or license review.
The user-selected model, revision and file list remain inputs to
`fetch_model_snapshot.py`; no weights or private project data are committed.

The second locked environment loaded this snapshot offline with the project's
current 13-label taxonomy. A one-token, in-memory forward/backward probe on CUDA
returned finite `[1, 13]` logits for 149,614,861 parameters; PyTorch reported
1,525,710,336 peak allocated CUDA bytes for that probe, including checks that
all produced gradients were finite. The classification head was newly
initialized. The [aggregate probe report](evidence/modernbert-gb10-runtime-probe.v2.json)
contains its identities. This is neither training nor a 512-token performance
measurement, and the untrained head cannot make qualified predictions.

On 2026-10-31, the trainer's explicit device selection was also checked in the
locked Spark environment without loading training examples or starting a run.
In the helper version used for that historical check, `cuda` selected `cuda:0`
and `cpu` selected `cpu`; with CUDA hidden, an explicit `cuda` request failed
before creating its output directory. That helper check did not establish that
the full trainer permitted CPU execution. The current trainer is GPU-only and
rejects CPU configuration for both GPU-present and GPU-absent hosts. This checks
target selection, not a completed training job or GPU
memory capacity. The selected target is a configurable run input documented in
the [trainer instructions](../../ml/lfg-encoder/README.md#checkpointing-and-restart).

A subsequent check on the same Spark exercised the current trainer's device
selection with the real Transformers `TrainingArguments` in the locked
environment. With the GB10 visible, both `auto` and `cuda` selected CUDA; with
`CUDA_VISIBLE_DEVICES=-1`, both were rejected. `cpu` was rejected in both cases.
The copied trainer had SHA-256
`da8c06f34e9e83a578072ee75176dfba7e31ffe8f36b4ea76f4f7765ce392ac4`.
No project examples were transferred and no model training took place.

Another local probe used the locked Transformers environment and the pinned
ModernBERT tokenizer with two texts already published in the LFG repository:
the kernel golden request and an authored boundary question. Their token lengths
were 9 and 19. The former default trainer collator failed to stack the batch;
dynamic padding produced a `[2, 19]` batch. With the updated trainer wiring, both
training and validation loaders produced that shape and the real ModernBERT
model returned finite forward losses on CUDA using a newly initialized head and
test-only labels. There was no optimizer step or reviewed-data training. The
optional `test_training_collation_runtime.py` check also passed on that locked
environment. This establishes batch mechanics for these inputs, not model
accuracy, training repeatability or capacity at production sequence lengths.

In the same locked Transformers environment, an isolated CPU fixture test
showed that the former schedule could finish before the first evaluation
interval: a one-step run with a 100-step interval saved a checkpoint but had
no evaluation event or selected best checkpoint. With the final-evaluation
callback, the checked-in runtime test exercised a one-step run, a final step
between intervals and a final step on an interval. Each evaluated the final
checkpoint and selected it when its fixture validation loss was best. The test
used a tiny fixture model and labels, not project data; it does not establish
accuracy or reproduce a real GPU training run.

Re-run the probe with the copied scripts and selected files in the isolated
directory, changing paths and settings as appropriate:

```bash
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 TOKENIZERS_PARALLELISM=false \
  venv-repro/bin/python probe_model_runtime.py \
  --model modernbert-base-v2 --model-manifest modernbert-base-v2.manifest.json \
  --revision 8949b909ec900327062f0ebf497f51aef5e6f0c8 \
  --taxonomy evaluation-taxonomy.v1.json --device cuda --threads 2 --tokens 1 \
  --seed 731 --output NEW_PRIVATE_REPORT.json
```

The actual project review workspaces still have zero approvals, and the
validation candidates come from one session. No persistent training service,
reviewed training run, full-length GPU benchmark, model quality result or
qualified CPU binary follows from these checks. A real run still needs reviewed,
authorized data and adequate label support, a durable supervised job with
resource isolation, independent evaluation, ONNX/CPU qualification and release
checks. Do not lower the review or quality gates to use this environment.

The trainer's versioned local-file marker now uses an operating-system lock.
On 2026-10-31, Windows and Spark tests verified that a second process is
rejected while the lock is held, that a hard-killed process releases it, and
that legacy and current trainers cannot simultaneously acquire the same output.
The review-workspace lock retains its previous behavior. An opt-in Spark systemd user-service
test killed its own fixture process while it held the lock; systemd restarted
the fixture once and the next process acquired it. The test unit reported the
configured CPU quota, memory limit, task limit and `NoNewPrivileges` setting,
then was stopped. It did not run training or test GPU memory isolation,
checkpoint recovery, host reboot, or a persistent production service. The user
manager reported lingering enabled and five pre-existing failed units whose
causes were not inspected. Rerun the opt-in check in a suitable Linux user
session with:

```bash
LFG_TEST_SYSTEMD_USER=1 python3 -m unittest discover -s ml/lfg-encoder -p test_systemd_training_lock.py
```

## Bounded training-step capacity on a second Spark

On 2026-10-31 `clyffy-03` was reachable with an NVIDIA GB10 and about 114 GiB
available host memory. Its compute-process list showed the remote desktop
service and no model-serving process immediately before and after these tests.
The already busy `clyffy-01` workload was not stopped. This is a point-in-time
observation, not a reservation or a guarantee that services were uninterrupted.

An isolated directory on `clyffy-03` received the pinned public ModernBERT
snapshot and the existing hash-locked wheelhouse. Offline installation passed
`pip check` and the installed-wheel payload verifier: 27,325 files and
5,107,746,248 bytes matched the locked payload, with 78 wheel records and three
scripts excluded. The [aggregate environment evidence](evidence/gb10-03-locked-environment.v1.json)
does not attest the interpreter, untracked files, external libraries or upstream
publisher. No private project requests or labels were copied to the host.

The runtime probe used repeated generated token IDs and generated zero labels,
the same pinned 13-label model configuration, and one forward/backward plus
AdamW step. The classification head was newly initialized; no weights were
saved. Each reported shape ran once in a fresh process using the canonical source
and taxonomy bytes; earlier checks used checkout bytes with different line endings.
All three reported finite logits,
loss and gradients before the step and initialized optimizer state:

| Tokens | Batch | Peak CUDA allocated | Peak CUDA reserved | Step time |
| --- | --- | --- | --- | --- |
| 512 | 8 | 4.41 GiB | 5.13 GiB | 1.87 s |
| 4,353 | 1 | 6.37 GiB | 7.21 GiB | 2.26 s |
| 8,192 | 1 | 8.77 GiB | 9.01 GiB | 3.98 s |

The [512-token](evidence/gb10-03-capacity-512-b8.v1.json),
[4,353-token](evidence/gb10-03-capacity-4353-b1.v1.json) and
[8,192-token](evidence/gb10-03-capacity-8192-b1.v1.json) reports bind the
model, taxonomy, probe and helper hashes. Each process used two CPU threads,
a 15% PyTorch CUDA allocator fraction, and a systemd scope with 28 GiB
`MemoryMax`, 400% CPU quota and 256 tasks. The allocator fraction is not GPU
isolation; cgroup limits do not by themselves establish a GPU memory limit.
Step time includes finite-gradient checks and synchronization; the samples were
not isolated or repeated under identical source identities and are not throughput
or performance guarantees. The timing excludes model loading and preparation.
The first attempted probe failed before model loading because the CUDA allocator
needed an explicit device index; the probe was corrected before these runs.

These tests do not exercise the full trainer, its data loader, checkpointing,
long-running stability, mixed lengths, validation, or model accuracy. They do
not train on project data or qualify a binary. Three pending real requests exceed
the selected model's 8,192-position configuration; the probe does not make them
fit or justify copying whole-request labels onto arbitrary segments. A reviewed
corpus and independent validation remain required.

To reproduce a bounded shape on a suitable idle host with the verified local
snapshot and locked environment, select the resource limits and output path for
that host and run the probe under the operator's scheduler, for example:

```bash
systemd-run --user --scope -p MemoryMax=28G -p CPUQuota=400% -p TasksMax=256 \
  env HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 TOKENIZERS_PARALLELISM=false \
  timeout 300 venv/bin/python probe_model_runtime.py \
  --model modernbert-base-v2 --model-manifest modernbert-base-v2.manifest.json \
  --revision 8949b909ec900327062f0ebf497f51aef5e6f0c8 \
  --taxonomy evaluation-taxonomy-v1-lf.json --device cuda --threads 2 \
  --tokens 8192 --batch-size 1 --seed 731 --cuda-memory-fraction 0.15 \
  --optimizer-learning-rate 0.00005 --optimizer-weight-decay 0 --output NEW_REPORT.json
```
