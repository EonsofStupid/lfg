# Reproducing the real-request CPU development run

This experiment checks repeatability of the existing below-gate run on one
Windows machine. It does not qualify the model, its unreviewed labels, or a
release. It does not use or modify the 226 pending review records.

## Locked training environment

The [Windows CPU Python 3.11 lock](../../ml/lfg-encoder/locks/windows-cpu-py311-experimental.requirements.txt)
binds 54 resolved wheels to exact versions and SHA-256 hashes. It is specific to
Windows x86-64 and this experimental CPU training environment; it is not a
Linux/ARM64 Spark lock or an ONNX export environment. The optional
`lock_wheelhouse.py` generates a new lock from operator-selected wheel files;
it rejects duplicate packages and creates the output exclusively. The lock
hashes the bytes it is given; it does not attest their publisher or provenance.

To acquire and use these exact wheels on a compatible machine, select an
appropriate package index, Python 3.11, an empty wheelhouse and a new virtual
environment. The initial acquisition can use a network; the installation
below uses only local files:

```powershell
py -3.11 -m pip download --only-binary=:all: --require-hashes `
  --dest WHEELHOUSE -r ml/lfg-encoder/locks/windows-cpu-py311-experimental.requirements.txt
py -3.11 -m venv VENV
VENV/Scripts/python.exe -m pip install --no-index --find-links WHEELHOUSE --require-hashes `
  -r ml/lfg-encoder/locks/windows-cpu-py311-experimental.requirements.txt
VENV/Scripts/python.exe -m pip check
```

The trainer checks the selected lock against the wheelhouse and compares the
installed distribution versions against it. For reviewed training it also
compares installed non-script wheel payload files with their locked wheel bytes
before and after training. This includes installed package source and native
extensions. Wheel `RECORD` files and wheel scripts are excluded because the
installer can rewrite them; their counts are reported. Generated bytecode,
generated entry points, untracked or shadowing files, allowed bootstrap
distributions, the interpreter, external native libraries, OS and processor are
not verified by this check. It does not prove upstream wheel provenance or
prevent concurrent modification; preserve installation evidence. Wheels with
unsupported data schemes fail the payload check. Installations and runs on
other machines still need verification. A changed wheel must fail the hash check:
this was tested locally by appending a byte to a copy of the `six` wheel, and
pip rejected it.

To check the installed payloads independently of a training run, invoke the
checker with the intended environment's interpreter:

```powershell
VENV/Scripts/python.exe ml/lfg-encoder/check_training_environment.py `
  --lock LOCK_FILE --wheelhouse WHEELHOUSE --allowed-extra pip
```

Specify `--allowed-extra` only for an explicitly permitted installed bootstrap
distribution. The check reads every included installed file and can take
several minutes. Its aggregate evidence is not a complete environment attestation.

## Bound training inputs

Prepare a local model directory containing the exact files needed by the
selected model and tokenizer. The directory cannot contain symbolic links or
Windows reparse points. Create its manifest outside that directory:

```powershell
python ml/lfg-encoder/training_inputs.py --model-dir LOCAL_MODEL_DIR `
  --model-id MODEL_ID --revision FULL_COMMIT_SHA --output NEW_MODEL_MANIFEST.json
```

For training, pass `--base-model LOCAL_MODEL_DIR`, `--model-revision
FULL_COMMIT_SHA`, `--model-manifest NEW_MODEL_MANIFEST.json`,
`--environment-lock LOCK_FILE`, and `--wheelhouse WHEELHOUSE`. Explicitly add
`--environment-allowed-extra pip` or another bootstrap distribution only when
it exists outside the lock. Unexpected or duplicated installed distributions,
version mismatches, wheelhouse drift, changed model files and extra model
directory entries reject the run. Reviewed training also requires the installed
wheel payload check. Below-gate runs can request it with
`--verify-installed-payload` when a wheelhouse and lock are supplied. The
installed version fingerprint, checked wheel payload digest and counts,
lock digest, model manifest digest and verifier code digests enter the run
manifest, so a changed input also rejects resume. Model loading is local-only
when a model manifest is supplied; its files are checked before loading and
again after training. Concurrent filesystem modification remains outside this
check's guarantees.

Reviewed training now requires these input options. Below-gate development runs
can omit them, but then have no corresponding input evidence. The model ID and
revision in the manifest are operator declarations, not verification of
upstream provenance. A model snapshot must be assembled and its source and
license reviewed independently.

On 2026-10-31 the installed payload check on the Windows CPU environment matched
25,295 files totaling 901,052,427 bytes against the 54 locked wheels. It excluded
54 installer records and three wheel scripts; one standalone check took about
211 seconds on this machine. A subsequent short training-path run with
test-only records and simulated review decisions completed both the pre- and
post-training payload checks and saved its model. Its recorded payload digest
matched the standalone check. This is evidence of the mechanism on that machine,
not a reviewed dataset, upstream authenticity, complete environment integrity,
or model quality. The real review workspaces still have no approvals.

On 2026-10-31, the previously described real-request CPU development run was
repeated with these checks enabled. A changed model file, a changed wheelhouse,
and an unlisted installed package were each rejected before their run directory
was created. A
second run was intentionally stopped after a complete step-six checkpoint,
then resumed in the other locked environment. Its final model weights,
tokenizer files, labels and run/split manifests matched the uninterrupted run;
the weight SHA-256 was the same `21dd6907...` value below. A subsequent resume
with an altered model manifest was rejected. These were actual runs over the
same 23 unreviewed development records, not independent quality evaluations.

## Observed local runs, 2026-10-31

Two independently created virtual environments installed the same 54 wheels
offline with `--require-hashes`; each passed `pip check`, and their installed
package lists matched. Both used Python 3.11.9, CPU-only PyTorch 2.14.1,
Transformers 4.57.6, and an Intel Core Ultra 9 275HX. The local wheelhouse held
252,324,852 bytes. The lock SHA-256 is
`a13aa8074c1ac0137d6b837967b72c80610deae61c0877eb0ce8701a22d9a69d`.

Both training runs used the exact private input and experimental settings in
the [real-request experiment](REAL-REQUEST-DEVELOPMENT-EXPERIMENT.md), including
the below-gate override. The input SHA-256 was
`6a5e0fbdd5caee3162f85524d1aaf29f24cfd7af39c9673cb79e068c71cbfe2a`.
They used trainer SHA-256
`2eefb42b8e9cfe285631e939ed8b1f30d5ad773f924a825c3941fa651fdbfe00`,
seed 730, three epochs, batch size two, maximum length 192, two CPU threads,
`PYTHONHASHSEED=730`, and Hugging Face offline mode. The base model was the
same locally cached revision described in the earlier experiment. The six
files below had the same hashes before, between and after the two runs:

The two runs produced byte-identical `model.safetensors`, model configuration,
tokenizer files, labels, split manifest and run manifest. The weights' SHA-256,
`21dd690709aa19a96265456c279674ecce14351e547e91c2c78aaa85e00ce5e8`,
also matched the earlier run on this machine. Other run files, such as trainer
state containing timings, were not claimed to match. The outputs and data remain
private under `target` and `dataset/private`.

For these earlier two runs, the base files were manually checked rather than
enforced by the trainer. The run manifest recorded selected package versions
rather than every installed file. These two runs share the same physical machine, Python installation and
model cache. They establish a useful local repeatability result for a tiny,
unreviewed experiment, not cross-machine determinism, representative quality,
security recall, Spark support, or a self-contained release.
